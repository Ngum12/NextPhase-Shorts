# Phase 2 increment: durable resumable uploads

This implements authenticated sequential uploads on the private local/shared
filesystem, with database-backed offsets and queue reservations. It does not
provision cloud object storage or background mobile transfer services.

## Upgrade

Stop API and worker, back up the actual database and media directory, pull the
merged code and run `PYTHONPATH=apps/api python -m app.migrate`. Revision
`0004_upload_sessions` adds tables/indexes without changing existing users/jobs
or download paths. Already versioned databases do not need legacy adoption again.
Run `npm ci` in apps/mobile, then restart API, worker and Metro with its cache
cleared. SDK-matched expo-crypto 15.0.9 supplies bounded chunk checksums and UUIDs;
keep the project's SDK 54-compatible Expo Go/development client.

Windows (after backup/pull, from repo root):

```powershell
$env:PYTHONPATH = "apps/api"
.\.venv\Scripts\python.exe -m app.migrate
cd apps\mobile
npm ci
npm run test:uploads
npm run typecheck
```

Compose retains the one-shot migration-before-API contract. API replicas/workers
must share the same database and **private storage volume**, and use consistent
settings. This is not a protocol for independent, unshared container disks.

## Protocol

All routes require bearer authentication and enforce the session's owner.
Another owner's or unknown session returns 404. Session identifiers and storage
paths are generated by the server; the original filename is never a storage path.

| Method / path | Behavior |
|---|---|
| POST `/api/v1/upload-sessions` | JSON file_name, total_bytes, title, style, desired_seconds; required Idempotency-Key; 201 new / 200 exact descriptor replay / 409 mismatch |
| GET `/api/v1/upload-sessions/{id}` | Authoritative received_bytes, negotiated chunk_bytes, expiry, state, eventual job_id and whole-source SHA-256; no local paths |
| PUT `/api/v1/upload-sessions/{id}/parts?offset=N` | Raw bytes plus required X-Chunk-SHA256; fixed-size part, except the final part; 200 with committed offset/checksum |
| POST `/api/v1/upload-sessions/{id}/complete` | Assemble and rehash committed parts, validate FFprobe metadata, atomically create one queued job and complete the session; repeated completion returns that same job |
| POST `/api/v1/upload-sessions/{id}/abort` | Repeat-safe abort/expiry and part cleanup; completed upload returns 409 (manage its render via the job) |

Session states are uploading, completed, aborted, expired. A partial or invalid
chunk never advances the offset. Exact replay of an already committed chunk is
accepted; different content at that offset, gaps or invalid boundaries return 409.
A conflict includes Upload-Offset when the client must query current progress.
Length/checksum mismatch returns 422; oversized part 413; transfer timeout 408;
expired session 410. Source max remains 300 MiB/10 minutes, with requested output
5–60 seconds and server-only 1080x1920 baseline rendering. Corrupt/missing stored
parts are rejected rather than rendered; the original committed chunk can repair
a part, or the user can discard and restart.

Bytes are staged without holding an owner lock. After length/SHA validation and
fsync, a short owner-serialized transaction atomically renames the immutable part
and inserts its metadata/advances the DB offset. A crash before DB commit can leave
an unreferenced part, but cannot acknowledge extra bytes; a lost acknowledgement
is recovered by GET/replay. Completion verifies every part and its total length,
computes a whole-source hash, fsyncs the assembled private input, then creates the
job and completes the session together. Unknown commit outcomes retain accepted
input rather than risk deleting it. Same-filesystem rename and durable DB/media
volumes are required; this is not cross-storage transactional replication or a
claim of survival after arbitrary hardware/filesystem failure.

## Capacity, expiry and cleanup

An unexpired uploading session reserves one of MAX_ACTIVE_JOBS_PER_USER slots
alongside queued/processing jobs. Legacy multipart admission checks those same
reservations. Completion exchanges its reservation for the job without counting
twice, even after limits are lowered for new submissions; abort/expiry releases it. Parallel session/legacy submissions cannot exceed
the configured owner limit. Declared source size is checked before accepting parts.

Defaults:

```dotenv
UPLOAD_CHUNK_BYTES=1048576
UPLOAD_SESSION_HOURS=24
UPLOAD_PART_TIMEOUT_SECONDS=120
```

Chunks may be configured from 64 KiB to 8 MiB, lifetimes 1–168 hours, timeouts
5–600 seconds. Chunk size is captured on each session and remains stable when
server defaults change. A chunk network receive holds no DB transaction; small
part publication/fsync and reservation transitions are owner-serialized. Lower
bandwidth may need a smaller configured chunk size. No part parallelism is needed.

Worker maintenance runs approximately once per minute while the worker is between
renders. It expires reservations and removes terminal staging directories/part
metadata in batches of 100; failed file deletion is retried. No worker means no
automatic cleanup. A render can delay that maintenance. Run manually if needed:

```bash
PYTHONPATH=apps/api python -m app.upload_cleanup
```

Completed job inputs/outputs are never removed by this cleanup. Session descriptor
and completion records remain for replay. Full account/media retention and deletion
are still future work. Admission reservations are not a global disk quota: legacy
multipart buffering, concurrent rejected requests, concurrent assemblies and
completed footage still need production edge/rate/storage controls. Do not expose
this prototype publicly.

## Mobile recovery and privacy

Create Short saves a private app copy of the selected file, then a per-account
pending intent before asking the server for a session. Two alternating metadata
journal slots retain the earlier valid record if the newest write is torn. No
bearer tokens/passwords are stored in these records. One pending intent per account
is supported in this UI; operations are guarded across screens.

The phone reads and hashes one bounded chunk at a time using native filesystem
and crypto APIs, then uploads it as binary. No full-video encoding, analysis or
inference occurs on the phone. Progress is server-acknowledged **upload bytes**,
not a fabricated render percentage. Pause aborts the current network request;
a resume first queries the authoritative offset. If a part or completion response
was lost, retry picks up committed progress/the original job. App restart recovery
uses the saved copy and session key; opening New Short offers Resume/Discard.

Transfers are foreground only; there is no promise of continuous OS background
upload. Keep app data and the saved private copy. App uninstall/data clearing,
missing files or both journal slots being damaged cannot be repaired automatically.
Local copies consume additional phone storage, up to the source cap per saved
account intent. They are removed after confirmed completion/discard; the intent remains retryable if local cleanup fails; the user's
original file is never deleted. An offline discard retains the saved state until
server abort can be confirmed. Interrupted preparation may leave a local orphan
copy; automatic local orphan retention cleanup is not included.

   large enough to span multiple chunks; only consented/synthetic footage.
2. Pause at an intermediate upload percentage. Resume and verify progress continues
   from the server's confirmed bytes rather than zero.
3. Repeat with USB disconnected midway; reconnect/reapply adb reverse, then resume.
4. Pause, force-stop Expo Go, reopen the same project, enter New Short and resume
   the saved upload. Do not clear app data. Confirm one project, successful render,
   authenticated download and playback.
5. Pause another upload and discard it. Verify its slot is freed and the original
   gallery file remains. Recheck old completed video downloads and job cancellation.

The owner reported successful Windows/Pixel acceptance after merging: upload,
pause/resume, saved-upload recovery, discard and render/download worked. These
are user-reported results, not native tests run by the cloud agent.

Backend tests and the actual API restart smoke cover server behavior. The six
mobile recovery tests use simulated native/network adapters across JS runtime
restarts; they verify the manager's protocol and journaling, not Android native
FileHandle/binary-fetch behavior, OS kill semantics or actual UI interactions.
